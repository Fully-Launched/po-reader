# PO-Reader

## Project Purpose

PO-Reader is an internal tool built for **Comfort x Design**, a single ServiceTitan customer, to automate the invoice-to-Purchase-Order workflow for their **3 non-integrated vendors** (vendors with no direct ServiceTitan integration, so invoices are currently keyed in by hand). Arco Supply Co. is the first confirmed vendor (real sample invoice received and validated). **Correction**: the other 2 vendors do NOT all use a nearly-identical format, as an earlier client call suggested — a later call confirmed real differences: "TEC" (Carrier) uses a different-enough format that it needs its own line-item handling (per-item Pricebook matching with a catch-all for anything unmatched, rather than Arco's full consolidation — see Business logic below), and invoices sometimes print the vendor text "Supply House," which is not itself a real ServiceTitan vendor (see the vendor remapping table below) but is treated the same as Arco for line-item purposes.

**Flow:**
1. User drags a vendor invoice PDF into the app.
2. The Claude API extracts structured invoice data from the PDF: vendor name, invoice number, invoice date, project number, line items (description, quantity, unit price, total), tax amount, freight/shipping amount (from the invoice's own `FREIGHT` line — CONFIRMED required, see the top-level-fields correction below), subtotal, total, plus an `extraction_confidence` rating and free-text `notes`.
3. A human reviews and corrects the extracted data in a fully editable table. Extraction is treated as a starting draft, not a pass/fail gate: `extraction_confidence` below `"high"`, a missing vendor name/project number, or no line items show a non-blocking warning banner (see `reviewWarnings` in `src/lib/servicetitan/payload-builder.ts`) but never disable the form — the user can add, remove, or correct any field, including ones the extraction missed entirely, before submitting. The only hard block is a document that isn't a vendor invoice at all (e.g. an internal memo) — see `isNotAnInvoice` — since there's no partial data worth editing in that case.
4. On confirmation, the tool resolves the ServiceTitan vendor (applying vendor remapping if needed), resolves the ServiceTitan job by project number (now REQUIRED, not best-effort), builds line items per the invoice's vendor-specific strategy, then creates a Purchase Order via `PurchaseOrders_Create`. See Business logic below.
5. **There is no separate "receive" step.** See the important correction below.

This is not a general-purpose product. It is built exclusively for Comfort x Design's ServiceTitan tenant and is not intended for redistribution or multi-tenant use.

### Important correction: how receiving actually works

An earlier version of this document assumed the tool would call a ServiceTitan "Receipts" endpoint after PO creation to receive the PO. **This is wrong and has been confirmed wrong against ServiceTitan's own developer docs.** Per their Inventory API resource page: *"A purchase order status cannot be updated through API."* There is no receive/status-change endpoint — full stop.

The **only** way a PO ends up `Received` (and, if enabled, auto-generates a bill) via the API is to **create it using a PO Type that has "Automatically Receive" enabled** — status and bill generation happen automatically at creation time, not via any follow-up call. In the sandbox, the PO Type named `"Supply House Run"` has this enabled. `buildPoPayload()` (`src/lib/servicetitan/payload-builder.ts`) requires a `poTypeId` for exactly this reason, and `/api/create-po` looks it up via `ServiceTitanClient.getPoTypeIdByName()`.

**Clarified on a client call: this app does not control or set receive status in any way.** "Automatically Receive" is a setting configured on the PO Type itself, inside ServiceTitan's own UI, on Kevin's account — not a field this app's payload sets. This app's only role is selecting which existing, already-configured PO Type to reference by name/ID. If Kevin ever changes which PO Type has this setting enabled, renames it, or disables it, this app has no way to detect that — `SERVICETITAN_AUTO_RECEIVE_PO_TYPE_NAME` would need updating to match. As a safety net for exactly this, the confirmation screen (`InvoiceUploader.tsx`) shows a permanent reminder to double-check the PO's receive status in ServiceTitan — this is deliberate and should stay even once the mechanism is reliably working, not be removed as "redundant" once things seem to work.

`ServiceTitanClient.updatePurchaseOrder()` exists in the client but is explicitly **not** for status changes — see the warning comment on that method.

### Important correction: line items need a real Pricebook skuId

An earlier version of `buildPoPayload()` (ported from the Python prototype) sent each line item as `{ skuName, quantity, price, total }`. **This is wrong** — a live `PurchaseOrders_Create` 400 confirmed the real required item properties are `cost`, `skuId`, `description`, and `vendorPartNumber`, not `price`/`skuName`. The field-name mismatch was the easy part to fix; the real issue is `skuId`: it must reference an **existing ServiceTitan Pricebook item**, not free text. Claude's extraction alone can never produce this — it has to be resolved via a lookup.

`ServiceTitanClient.findMaterialSkuIdByDescription()` does a **naive, first-pass** description-text match against Pricebook Materials (using the Read-only Pricebook scope already granted). Calling it per-item for EVERY invoice was the original stopgap; **CONFIRMED on a client call that this is not the right strategy for every vendor** — see the "Business logic" section below for the real, now-decided per-vendor strategy (bulk consolidation for Arco/Supply House, per-item + catch-all for TEC, this naive per-item matching only as the strict fallback for anything else). `/api/create-po` still fails with a clear `422` naming exactly which line-item descriptions had no Pricebook match when the strict path is used, rather than either guessing a SKU or letting the raw ServiceTitan 400 surface confusingly.

`ExtractedInvoice`'s line items also gained a `vendorPartNumber` field (the vendor's own part code, e.g. Arco's `"301/D"`) since ServiceTitan requires it per item — this is separate from, and does NOT help resolve, the Pricebook `skuId`.

### Important correction: top-level fields — shipTo, shipping, requiredOn, inventoryLocationId, impactsTechnicianPayroll

Once item-level validation passed, a **second** live `PurchaseOrders_Create` 400 surfaced five more required top-level fields the payload was missing entirely — the prototype never sent any of these. **All of the shape questions below are now CONFIRMED** — a full end-to-end sandbox test succeeded (PO #19969, all 56 line items from a real Arco Supply invoice, correctly auto-received, total `$4,411.64` matching the source invoice exactly). What's still open is real *content* for some of these fields (the client's real address, real freight-cost handling), not their shape — see Open Questions.

- **`inventoryLocationId`** — resolved the same way as `businessUnitId`: a dropdown in the review table (`GET /api/inventory-locations` → `ServiceTitanClient.listInventoryLocations()`), the user picks a name, never a raw ID. **The endpoint changed once already**: the original guess (`GET .../inventory-locations`) 404'd live. It's now `GET /inventory/v2/tenant/{tenant}/warehouses` — CONFIRMED working against the live sandbox as part of the PO #19969 test above. Still unconfirmed for the client's **production** tenant (same endpoint, but production account's Inventory Location count/names not yet confirmed) — see Open Questions.
- **`impactsTechnicianPayroll`** — hardcoded to `false` in `buildPoPayload()`. **Confirmed on a client call, no change**: even though a job is now always attached (see Business logic below), these are material/restock purchases, not technician labor, so there's no payroll to impact.
- **`requiredOn`** — **CONFIRMED genuinely user-editable**, not a hardcoded placeholder anymore. A date input in the review table (`ReviewTable.tsx`) defaults to today (`todayLocalDate()`) but allows selecting any date, including past dates — the plain `<input type="date">` has no `min`/`max`, and this was a deliberate client requirement (Kevin needs to be able to backdate it). Threaded through `onConfirm` → `/api/create-po`'s `requiredOn` body field → `buildPoPayload()`'s `requiredOn` arg, which now requires it rather than computing a default internally.
- **`shipTo`** — shape CONFIRMED via a live 400: it's a nested wrapper, `{ address: {...}, description: "..." }`, not a flat address object as first guessed. A follow-up live 400 further confirmed the nested `address` object's `unit` field must not be `null` ("shipTo.Address.Unit is required") — fixed by sending `unit: ""` instead. Both fixes are in `CLIENT_SHIP_TO_ADDRESS`/`buildPoPayload()` in `payload-builder.ts`, and the full shape is what PO #19969 succeeded against. **Both the address CONTENT and the description are CONFIRMED REAL client data, not placeholders**: the address is `"Comfort X Design, Inc." / 510 S Spring Road / Elmhurst, IL 60126`, no unit/suite (confirmed on a client call); the description is `"Main Office"` (`SHIP_TO_DESCRIPTION` in `payload-builder.ts`, replacing an earlier leftover `"Sandbox test PO"` value that was confirmed visible on a live PO's "Ship To" label — see the corresponding Status Checklist entry). Both are used in every environment, not sandbox-only.
- **`shipping`** — shape CONFIRMED via a live 400 ("Could not convert string to decimal: Ground"): it's a plain **numeric** field (a freight/shipping cost as a decimal), not an address object and not a carrier/method string as first guessed. **CONFIRMED on a client call: this must come from the invoice's own `FREIGHT` line, not be hardcoded.** `ExtractedInvoice` gained a `freightAmount` field (`src/lib/types.ts`), extracted by Claude (`extraction.ts`'s `freight_amount`, usually `0.00` but not assumed to be), and shown as an editable "Freight / shipping" input in the review table — `buildPoPayload()` now sends `invoice.freightAmount ?? 0` instead of a hardcoded `0`.

On the generic **`"request"`** field: **CONFIRMED resolved by sending an empty object, `request: {}`, permanently.** Once shipTo/shipping were fixed and `request: {}` was added, PO #19969 succeeded with no further error naming `request`. **Confirmed on a client call that Kevin doesn't know what this field is either** — there is nothing further to investigate here from either side. `REQUEST_PLACEHOLDER = {}` in `payload-builder.ts` is a permanent fixture now, not a TODO.

## Business logic

Three vendor-specific rules, all **CONFIRMED on a client call**, that don't fit the generic "extract → review → submit" flow described above — how a PO gets built now depends on *which vendor* the invoice is from. This section replaces an earlier "Job attachment is optional, not required" section — that framing is now wrong, see below.

### Vendor remapping

Some invoices print a vendor name that isn't itself a real ServiceTitan vendor. **CONFIRMED**: invoice vendor text `"Supply House"` actually resolves to the ServiceTitan vendor **`"Chase"`**. `src/lib/servicetitan/vendor-remap.ts`'s `resolveServiceTitanVendorName()` is a small, deliberately extensible lookup table (`VENDOR_REMAP_RULES`, not an inline if-check) for this — `/api/create-po` calls it right before `findVendorByName()`, so vendor *resolution* uses the remapped name. Line-item strategy (below) still keys off the invoice's own original vendor text, not this remapped name, since the original text is what determines the invoice's *format*, not which real ServiceTitan vendor it bills to.

**CORRECTED after a live bug report**: the original version matched on the EXACT string `"supply house"` (lowercased/trimmed) — it failed on a real invoice printing `"SupplyHouse.com"` (no space, `.com` suffix), which fell through unmapped and 404'd on vendor lookup. Fixed by normalizing (lowercase, strip all non-alphanumeric characters) BOTH the alias and the invoice text, then matching the alias as a SUBSTRING of the normalized invoice text, not exact equality — `"supplyhouse"` now matches `"SupplyHouse.com"`, `"Supply House"`, `"Supply House, Inc."`, etc. regardless of spacing/punctuation/suffixes. Verified with a standalone test importing the real function (not a reimplementation) against 7 cases including the exact failing real-invoice string, an unrelated vendor, and an unmapped one — all passed, no false positives.

**TEC IS now in this table**, per explicit client instruction: any vendor text containing "TEC" (substring match, e.g. "TEC Distribution", "TEC Excelsior") maps to ServiceTitan vendor `"TEC"` directly — **NOT independently verified against a live `findVendorByName()` lookup**, since that was (and still is) blocked on sandbox credential access (see Open Questions). Known gap: "National Excelsior Co." (one of the candidate names the client mentioned) contains no "tec" substring, so it would NOT match this rule if that turns out to be the real printed variant — update `vendor-remap.ts` if/when that's confirmed to happen.

**Same substring-matching fix also applied to line-item strategy selection** (`line-item-strategy.ts`'s `resolveLineItemStrategy()`) — it had the IDENTICAL exact-string-match bug, just not yet caught live: `BULK_CONSOLIDATION_VENDOR_NAMES`/`CATCH_ALL_VENDOR_NAMES` were exact-match `Set`s, so `"SupplyHouse.com"` would have silently fallen through to the wrong (`strict`) strategy the same way it 404'd on vendor lookup. Both modules now share one normalize+substring implementation (`vendor-name-matching.ts`) rather than two separate copies of the same matching logic.

### Per-vendor line-item matching strategy

The original "match every line item individually against the Pricebook, fail if any don't match" approach (see the Pricebook `skuId` correction above) was always flagged as a stopgap, not the real strategy — and it turned out to be wrong for two of the three vendors. `src/lib/servicetitan/line-item-strategy.ts`'s `buildLineItemsForVendor()` now branches on the invoice's own vendor text (`resolveLineItemStrategy()`):

- **`"ARCO SUPPLY CO"` and `"Supply House"`** (`bulk-consolidation`) — ALL extracted line items are consolidated into a SINGLE PO line item: description `"Bulk Rough Material"`, quantity `1`, `cost` = the sum of every line item's own `total`. No individual Pricebook matching is attempted for these vendors at all.
- **`"TEC"`** (Carrier; `catch-all`) — keeps the original per-item Pricebook matching for items that DO find a match. An item that doesn't match is no longer a hard failure — unmatched items are consolidated into one catch-all line, description `"Bulk Equipment Material"`, quantity `1`, `cost` = the sum of the unmatched items' `total`s.
- **Anything else** (`strict`, the original/default behavior) — every line item must individually match a Pricebook item, or the whole submission fails with a `422` naming exactly which descriptions had no match. This is the fallback for any vendor not covered by either rule above (there are only 3 vendors total for this tool — see Project Purpose — so today this only matters if a vendor's extracted name text doesn't match the expected strings above, e.g. a typo/variant).

**Both `"Bulk Rough Material"` and `"Bulk Equipment Material"` must exist as real Pricebook Material entries in Kevin's ServiceTitan tenant** — `skuId` is still hard-required per item (confirmed via a live 400 earlier, see the Pricebook `skuId` correction above), so these consolidated lines need a real Pricebook item to resolve against just like any other line item. Creating/maintaining those two catch-all Pricebook entries is Kevin's responsibility, not something this app does — if either is missing, `/api/create-po` fails clearly naming which one.

### Job attachment is now required

**CHANGED from best-effort/optional to REQUIRED on a client call**: every PO must now be tied to a specific ServiceTitan job. Kevin is switching his invoice PO numbering to use the project number directly, so the invoice's extracted `project_number` is now expected to match an existing ServiceTitan job's Job Number one-to-one, for every invoice.

- `hasRequiredFields()` (`payload-builder.ts`) now requires `invoice.projectNumber` — previously deliberately NOT required, back when job attachment was optional.
- `ServiceTitanClient.findJobByProjectNumber()` (`client.ts`) is now actually implemented, not a stub that throws. Researched with the same rigor as the earlier warehouse-endpoint research (cross-referencing three independent third-party sources, since ServiceTitan's own developer docs are a JS-rendered page that can't be fetched directly), which correctly concluded there's no documented server-side filter to look up a Job by number — so this method **paginates** through `GET /jpm/v2/tenant/{tenant}/jobs` and matches client-side, capped at 20 pages (2,000 jobs) to avoid a runaway loop. **CORRECTED after a live bug report**: the field name the research guessed (`number`) was WRONG — two of the three third-party sources both guessed "number" and both were wrong. A live sandbox test failed to match real, confirmed-existing job numbers (1817/2117, visible in ServiceTitan's own Purchase Orders "Job No." column); diagnostic logging of a raw job object confirmed the real field is **`jobNumber`** (e.g. `jobNumber: "1717"`), now fixed. **Also CONFIRMED live**: pagination isn't currently an issue — the sandbox's full 55-job list fits on page 1 with `hasMore: false` — but the pagination/MAX_PAGES safety net is kept in for larger real accounts, not removed just because it wasn't exercised here. See the method's doc comment in `client.ts` for the full trail.
- `/api/create-po` now fails the request with a clear `422` naming the project number if no matching job is found, rather than silently proceeding without one (the old best-effort behavior). `buildPoPayload()`'s `jobId` argument is no longer optional.
- `impactsTechnicianPayroll` stays hardcoded `false`, unchanged — see the top-level-fields correction above.

## Multi-invoice batch flow

**CONFIRMED real constraint (a live Arco sample)**: vendor invoices don't always arrive one-PDF-per-invoice. Arco's real delivery is ONE PDF containing multiple separate invoices back-to-back (a monthly statement) — up to 18 invoices in the observed sample, ranging 2 to 20+ in general, with:

- A **cover/summary page** sometimes first (e.g. an index listing the invoice numbers in the bundle) — NOT an invoice itself, must be detected and skipped.
- **Variable page count per invoice** — 1, 2, 3, or more pages each, not fixed or predictable, and not uniform even within the same bundle.

### Design: two-pass extraction, not one combined call

A single Claude call trying to both find AND fully extract every invoice in an 18+ invoice bundle risks exceeding `max_tokens` (extraction output for just ONE 56-line-item invoice already needs the full 16000-token ceiling) — so this is deliberately a **two-pass** design, not one giant call:

1. **`detectInvoiceBoundaries()`** (`src/lib/extraction.ts`) — a lightweight first pass over the WHOLE document. Asks Claude to identify each invoice's page range by looking for repeating structural signals (a new "INVOICE" header, a new invoice number, a new date, a new "Bill To" block) rather than assuming a fixed page count, and to skip any cover/index page entirely (not reported as an invoice, not included in any range). Output is tiny (just page ranges + an optional preview invoice number per invoice) — `max_tokens: 4000` is generous headroom, never close to truncating regardless of bundle size, since it never contains line items or totals.
2. **Per-invoice extraction, split out and lazy** — each detected boundary is later turned into its own standalone PDF (`splitPdfPageRange()` in `src/lib/pdf-split.ts`, using `pdf-lib`) and run through the EXISTING, unmodified `extractInvoice()` — the exact same function and schema the single-invoice flow always used. This is NOT done eagerly for every invoice in the bundle up front: each one is only extracted when the user actually opens it for review (see Frontend below) — avoids wasting API calls/cost on invoices the user might not get to today, and avoids a large bundle's *combined* extraction time exceeding a single request's budget (Vercel `maxDuration`).

A single-boundary result (the common case: an upload that's just one invoice) is treated as "not a bundle" and falls straight through to the ORIGINAL single-invoice flow — `/api/extract-invoice` on the whole file directly, unchanged from before this feature existed. **Tradeoff accepted**: every upload now pays for one extra lightweight `detectInvoiceBoundaries()` call before the real extraction, even genuinely single-invoice ones — kept simple rather than adding a page-count heuristic to skip it, since this is a low-traffic internal tool; revisit if extraction latency/cost becomes a real concern.

### Frontend: a strict linear flow, not a jumpable queue

**CHANGED after live testing surfaced two bugs**: an earlier version of this flow was a free-form queue — a list of every detected invoice, each reviewable in any order via a per-row "Review" button, with a manual "Review next invoice" shortcut and a return to that list after every submission. Live testing found this let a user submit invoices out of order, lose track of which ones were already done, and — combined with the submission-feedback bug below — click "Create purchase order" a second time before the first request had resolved. Both problems are fixed by removing the queue UI entirely in favor of a strictly linear, one-invoice-at-a-time flow with no way to jump around or go back.

`InvoiceUploader.tsx` still gets a `batchQueue: QueuedInvoice[] | null` (null = not a bundle, single-invoice behavior identical to before), but there is no longer a queue *screen*:

- The moment a bundle is detected, the FIRST invoice is immediately, automatically extracted (lazily, via `/api/extract-invoice-page-range` — same lazy-per-invoice mechanism as before) and shown for review. The user never sees or clicks through a list.
- `BatchInvoiceScreen` (replacing the old `BatchQueueScreen`) shows only the CURRENT invoice — a header states the total count and current position ("3 invoices detected... reviewing invoice 1 of 3"), then either a loading state, an error state with a "Retry" button, or the SAME `ReviewTable` component the single-invoice flow uses, unmodified except for an optional `cancelLabel` prop (used when a queued item turns out not to be a real invoice at all — see below).
- Submitting creates one PO via the SAME `/api/create-po` call as always. The moment that response comes back successfully, the flow **automatically** extracts and advances to the next invoice — no manual "review next" click, and no control anywhere lets the user return to an invoice whose PO was already created.
- Once the LAST invoice's PO is created, the app **automatically** navigates to the "Confirmation" tab, which shows `BatchSummaryScreen` (all created PO numbers/vendors at a glance) instead of the single-PO `ConfirmationScreen` — no manual click required to get there either.
- A queued invoice that fails `isNotAnInvoice()`'s hard-block check (e.g. a misdetected cover/index page) can be skipped via `cancelLabel="Skip this invoice"` on `ReviewTable`, which marks that slot `"skipped"` and auto-advances exactly like a real submission would — `BatchSummaryScreen` lists it as "Skipped" rather than a PO number. This is the one case (not a live client requirement, just a necessary fallback for a rare edge case) not directly covered by the linear redesign's own spec.
- The queue still lives in `InvoiceUploader.tsx`'s top-level React state (not inside a tab-specific child), so switching tabs (e.g. to Dashboard and back) doesn't lose progress on the CURRENT invoice being reviewed.

**Known limitation, not fully solved**: this queue state does NOT survive an actual page reload/browser refresh — there is still no persistence layer anywhere in this app (see the recurring theme throughout this doc: no database, no activity log). A hard refresh loses the queue and the user would need to re-upload the PDF. Fixing that fully would need either a real backend persistence layer, or client-side storage of both the queue metadata AND the original PDF bytes (e.g. IndexedDB, which unlike `localStorage` can hold large binary blobs) — out of scope for this pass, flagged in Open Questions.

### Submission feedback bug (fixed)

**CONFIRMED real, found in live testing**: clicking "Create purchase order" sometimes gave no clear feedback that a submission was in progress or had succeeded, so the user clicked it again — which could fire a second real `PurchaseOrders_Create` request and create a genuine duplicate PO in ServiceTitan before the first request had resolved. The root cause is a classic React race, not a missing UI element: `ReviewTable.tsx` already disabled its submit button and showed "Creating purchase order..." while a `submitting` boolean (React state, passed down from `InvoiceUploader.tsx`) was true — but state updates from `setSubmitting(true)` aren't applied until AFTER the click handler that triggered them returns, so two click events arriving close together could both read `submitting` as still `false` and both go on to fire `fetch("/api/create-po")`.

Fixed with a synchronous re-entrancy guard in `InvoiceUploader.tsx`'s `handleConfirm()`: a `useRef` boolean (`submittingRef`), checked-and-set as the very first statement, before any state update or `await`. Refs are mutated synchronously and aren't tied to React's render cycle, so a second call arriving before the first one's `submitting` state has actually rendered is a no-op rather than a second network request — this closes the race regardless of render timing, not just in the common case. `submitting` (the React state) is kept as-is for what it's good at: driving the button's disabled/loading UI.

The batch queue's per-invoice status was already, and remains, driven strictly by the actual `/api/create-po` response — a slot is only ever marked `"submitted"` inside the `res.ok` branch, after the real response body has come back, never optimistically before the request resolves and never assumed on a client-side timeout. A network failure (the `catch` branch) reports a submission error without touching that slot's status at all, so a slot can never show "PO created" for a request that actually failed, or vice versa.

## Architecture

- **Framework:** Next.js, deployed to Vercel.
- **App Router** is used for routing.

### Core library code (`src/lib/`)

This logic was ported from an earlier Python prototype (`comfort-x-design-invoice-tool`) that was validated against a real Arco Supply invoice sample — it isn't from-scratch/unvalidated code, and the TODOs below reflect genuine open items from that prototype, not just caution.

- **`src/lib/types.ts`** — `ExtractedInvoice` / `InvoiceLineItem`, the shape that flows extraction → review table → PO creation. `InvoiceLineItem.lowConfidence` is a PER-ITEM flag, distinct from `ExtractedInvoice.extractionConfidence` (a single whole-document rating) -- lets the review table flag exactly which line item(s) Claude itself was unsure about (see `reviewWarnings()` and `ReviewTable.tsx`'s per-row amber border below), not just a generic "something might be off" banner.
- **`src/lib/error-messages.ts`** — the style guide (as a doc comment) every user-facing error message in this app follows, plus two small shared helpers (`notFoundError()`, `upstreamFailureError()`) for the two most common message shapes. Established so future error messages are consistent with each other rather than each written ad hoc -- see the reference example in the doc comment (the job-not-found message in `/api/create-po`).
- **`src/lib/extraction.ts`** — `extractInvoice(pdfBuffer)`: sends the PDF to Claude with a defined extraction prompt/JSON schema, parses and normalizes the response into `ExtractedInvoice`. `detectInvoiceBoundaries(pdfBuffer)`: the lightweight first-pass boundary scan for bundled PDFs -- see Multi-invoice batch flow above. Both share a `validatePdfSignature()` helper.
- **`src/lib/pdf-split.ts`** — `getPdfPageCount()` / `splitPdfPageRange()` (via `pdf-lib`): extracts a page range out of a PDF into its own standalone PDF, so a bundled invoice can be run through the exact same `extractInvoice()` the single-invoice flow always used. See Multi-invoice batch flow above.
- **`src/lib/servicetitan/client.ts`** — `ServiceTitanClient`: OAuth2 `client_credentials` token fetch/cache, `createPurchaseOrder`, `getPoTypeIdByName`, `findVendorByName`. `findJobByProjectNumber` **is now implemented** (paginate-and-match against `GET /jpm/v2/tenant/{tenant}/jobs`, see Business logic below) — its caller in `/api/create-po` now treats a missing job as a hard `422` error, since job attachment is required, not best-effort.
- **`src/lib/servicetitan/vendor-name-matching.ts`** — `normalizeVendorName()` / `matchesAnyAlias()`: shared fuzzy (normalize + substring, not exact-equality) matching used by both `vendor-remap.ts` and `line-item-strategy.ts`, so a real invoice's exact spacing/punctuation/suffixes don't need to match a hand-typed alias exactly. See Business logic below for the bug this fixed.
- **`src/lib/servicetitan/vendor-remap.ts`** — `resolveServiceTitanVendorName()`: small extensible lookup table mapping an invoice's extracted vendor text to the real ServiceTitan vendor name to resolve against (e.g. `"Supply House"` → `"Chase"`, any `"TEC"`-containing name → `"TEC"`). See Business logic below.
- **`src/lib/servicetitan/line-item-strategy.ts`** — `buildLineItemsForVendor()`: builds the PO's `items[]` array per the invoice's vendor-specific strategy (bulk consolidation, per-item + catch-all, or strict per-item matching). See Business logic below.
- **`src/lib/servicetitan/payload-builder.ts`** — `buildPoPayload()` converts an `ExtractedInvoice` + resolved IDs/items into the `PurchaseOrders_Create` request body; `jobId` is now REQUIRED (no longer optional/omittable — see Business logic below); `items` is a pre-built `PoLineItem[]` from `buildLineItemsForVendor()`, not computed in here; `inventoryLocationId` is required; `impactsTechnicianPayroll` is hardcoded, `requiredOn` is a required caller-supplied arg (genuinely user-editable, see Frontend below), `shipTo`/`shipping` use the confirmed real client address/freight amount (see the important correction above). Three review/guardrail functions, all pure (safe to call from client or server code): `reviewWarnings()` / `needsHumanReview()` are non-blocking — they surface a warning banner but never disable submission. **CONFIRMED on a client call: this banner covers ONLY line-item extraction accuracy** (the per-item `InvoiceLineItem.lowConfidence` check, distinct from the whole-document `extractionConfidence` field) — every other check this used to include (missing vendor name, missing project number, no line items, generic whole-document confidence) was deliberately removed, since those are either already surfaced as a red-bordered required field in `ReviewTable.tsx` or not worth a banner mention; `isNotAnInvoice()` is the one hard-block gate (document isn't a vendor invoice at all); `hasRequiredFields()` is the actual submission gate (vendor name, project number, and at least one valid line item present — project number is now REQUIRED, changed on a client call, since job attachment depends on it).

### API Routes

- **`/api/detect-invoice-boundaries`**
  Accepts a PDF upload, calls `detectInvoiceBoundaries()`, returns `{ boundaries: InvoiceBoundary[] }`. Called FIRST on every upload, before any full extraction — see Multi-invoice batch flow above. A single-boundary result means "not a bundle."

- **`/api/extract-invoice`**
  Accepts a PDF upload (`multipart/form-data`, field `file`), calls `extractInvoice()`, returns the structured `ExtractedInvoice`. Used for the whole file in the single-invoice case (`boundaries.length <= 1`).

- **`/api/extract-invoice-page-range`**
  Accepts a PDF upload plus `startPage`/`endPage`, splits out that page range (`splitPdfPageRange()`), runs the SAME `extractInvoice()` on the sub-PDF, returns the `ExtractedInvoice`. Used per-queued-invoice, lazily, in the multi-invoice batch flow — the client re-sends the full original file each time rather than the server caching split pages between requests (no persistence layer exists to cache anything server-side, consistent with the rest of this app).

- **`/api/create-po`**
  Takes the human-reviewed `ExtractedInvoice` (plus `businessUnitId`, `inventoryLocationId`, and `requiredOn` — see below), resolves the ServiceTitan vendor via `findVendorByName` (using `resolveServiceTitanVendorName()`'s remapped name — required), resolves the job via `findJobByProjectNumber` (REQUIRED — fails with a `422` if no matching job is found, see Business logic above), resolves the auto-receive PO Type ID, builds `items[]` via `buildLineItemsForVendor()` per the invoice's vendor-specific strategy (fails with a `422` naming the issue if a required catch-all Pricebook item is missing or, for the strict fallback, any line items didn't match — see Business logic above), builds the payload, and calls `PurchaseOrders_Create`. Re-runs `isNotAnInvoice` and `hasRequiredFields` server-side as defense in depth even though the frontend should already gate on the same checks — does NOT re-check confidence, since low confidence is not a submission blocker (see Flow above).

  **`businessUnitId` and `inventoryLocationId` come from the review table's dropdowns** (see Frontend below), populated via `GET /api/business-units` and `GET /api/inventory-locations` respectively.

- **`/api/business-units`**
  `GET` — calls `ServiceTitanClient.listBusinessUnits()` and returns `[{ id, name }, ...]`. Backs the review table's Business Unit dropdown; the user picks a name, never types or sees a raw ID. Supersedes an earlier temporary `/api/dev/business-units` scratch route (now deleted) that was sandbox-only — this one is permanent and has no environment restriction, since Business Unit selection is needed in every environment.

- **`/api/inventory-locations`**
  `GET` — calls `ServiceTitanClient.listInventoryLocations()` and returns `[{ id, name }, ...]`. Same pattern as `/api/business-units`, backing the review table's Inventory Location dropdown.

### Frontend

The UI is built from a design mockup (`po-generator-draft.html`, not part of this repo — a static HTML/CSS prototype with example/placeholder data) — the CSS design system (colors, spacing, typography: Inter + IBM Plex Mono via Google Fonts, tabler-icons via CDN) was ported into `src/app/globals.css` and `src/app/layout.tsx`, and the three screens (Dashboard, Review invoice, Confirmation) into the components below. It's a single-page app shell with a nav-rail + tabs, not multiple Next.js routes.

- **`src/components/InvoiceUploader.tsx`** — the app shell: nav-rail, tabs, branded header, footer, and the upload → extract → review → submit state machine. Renders one of three screens depending on progress. Real, functional differences from the static mockup (which just lets you click freely between screens):
  - **Tabs/nav-rail are gated by actual progress**, not freely clickable — `canGoTo()` only allows "Review invoice" once an invoice is loaded and not yet submitted, and "Confirmation" only once a PO actually exists. Jumping to a screen with no backing data isn't possible.
  - **The mockup's Dashboard has a "This week" activity log with example rows** (e.g. "Arco Supply · INV-23538 · Received"). This app has no persistence layer to back a real activity log, so it's **omitted** rather than shown with fabricated data — add it back once there's a real data source (see Status Checklist).
  - **A failed PO submission keeps the user on the Review screen** with their edits intact and an inline error (`ReviewTable`'s `submitError` prop), rather than a generic error screen that would discard the draft — the mockup has no error state to model this against, and losing a hand-corrected draft on a transient failure would be a real regression.
  - **Drag-and-drop is implemented** on the dropzone (the mockup's dropzone was styled but non-functional demo markup).
  - **"View in ServiceTitan" on the confirmation screen links to the created PO** using a CONFIRMED real deep-link pattern (client, live-tested) — see Open Questions for the full trail and `ServiceTitanClient.buildPurchaseOrderViewUrl()`. Falls back to a disabled button with an honest tooltip only if the create-po response had no usable internal id.
  - **Multi-invoice bundle support is entirely new, not in the mockup at all** — see the "Multi-invoice batch flow" section above for the full design. A bundled upload gets a strictly linear `BatchInvoiceScreen` (one invoice at a time, auto-advancing, no jumpable list) and, once everything's submitted, a `BatchSummaryScreen` in place of the single-PO `ConfirmationScreen`. A single-invoice upload is completely unaffected — same `ReviewTable`/`ConfirmationScreen` as always.
  - Confirmation copy says "created and auto-received" — deliberately does NOT say "and billed automatically" (unlike a first instinct might suggest), since whether a bill auto-generates on receipt depends on the client's Inventory Configuration setting, which is still an open, unconfirmed question (see Open Questions) — the UI shouldn't claim something as fact that the codebase itself flags as unconfirmed.

- **`src/components/ReviewTable.tsx`** — the "Review invoice" screen. This is the human-in-the-loop checkpoint: nothing is written to ServiceTitan until the user confirms/corrects the extracted data and picks a Business Unit and an Inventory Location from their respective dropdowns (not in the original mockup, which didn't model these fields — added since they're real required fields for `PurchaseOrders_Create`; fetched on mount via the shared `useIdNameOptions` hook, and if only one option exists for either, it's pre-selected automatically but still shown, not hidden). Also includes a `Required on` date input (defaults to today via `todayLocalDate()`, no `min` — backdating is a confirmed client requirement) and a `Freight / shipping` number input bound to `ExtractedInvoice.freightAmount`. Tax (`taxAmount`) is a real editable input here too, and flows unmodified through `onConfirm` → `/api/create-po` → `buildPoPayload()`'s `tax: invoice.taxAmount` — audited end-to-end, not just displayed. Shows the `reviewWarnings()` banner (green "accuracy check passed" when empty, amber warning list otherwise — now ONLY line-item accuracy, see the payload-builder.ts bullet above) plus an amber left-border on any individual line-item row where `lowConfidence` is true. A Pricebook match-count indicator ("X/Y items matched to Pricebook, Z/Y added to bulk material") shows for TEC-style catch-all invoices only, via `/api/line-item-match-preview` (reuses `buildLineItemsForVendor()`, doesn't reimplement matching) -- fetched once on load, with a manual "Recheck" button. Submission calls `/api/create-po` with `{ invoice, businessUnitId, inventoryLocationId, requiredOn }`; a submission failure (`SubmitError { message, field? }`) shows in the error banner and, when the API named a specific field (currently `vendorName`/`projectNumber`), puts a red border on that exact input -- see `error-messages.ts`. **Red-border state is PROACTIVE, not just reactive**: `vendorNameInvalid`/`projectNumberInvalid` (and each line item's description/quantity inputs) turn red as soon as the screen loads with that field empty/invalid, mirroring `hasRequiredFields()`'s own checks, not only after a failed submission names that field.

The review screen is a deliberate design choice, not a placeholder to be removed later — Claude's extraction is not assumed to be perfect, and PO creation (which, per the correction above, auto-receives and can auto-bill) is not something we want to auto-fire on unverified data.
